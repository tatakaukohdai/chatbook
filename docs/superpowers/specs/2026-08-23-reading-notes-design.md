# 読書メモ機能 設計

- 種別: 確定設計（実装前）
- 対象: AI チャットとは別に、本ごとの Markdown 読書メモを取れるようにする機能
- 最終更新: 2026-08-23（Codex のレビューを反映して清書）
- 前身: [`2026-08-19-reading-notes-design.md`](./2026-08-19-reading-notes-design.md)（検討段階。「決定待ち」を含む）

本を読みながら自分の言葉でメモを取り、PDF の選択箇所とチャットの往復をそこへ集める。
前身が残していた 5 つの決定待ちはすべて埋め、**AI がメモを書き換える経路（前身の Phase 4）は
落とした**。この文書が正で、前身は検討の記録として残す。実装前レビューの指摘は本文へ織り込み、
何がどう変わったかは末尾の「付録: レビューで変わったこと」にまとめてある。

機能そのものは素直だが、**保存と競合の扱いは単純な CRUD ではない**。難しさはそこに集中している。

## 何を作るのか

**本ごとに 1 枚の Markdown 文書。** メモが埋まる経路は 4 つで、書き手はどれも読者である。

| 経路                 | 入口                                              | 着地                                        |
| -------------------- | ------------------------------------------------- | ------------------------------------------- |
| 自分で書く           | 右ペインのメモタブ（広い画面のみ）                | キャレット位置                              |
| PDF の選択箇所を挿入 | `SelectionPopover` / `SelectionActionBar`         | キャレット位置。フォーカスが無ければ末尾    |
| クイックメモ         | 狭い画面の 1 行入力欄（選択箇所を伴うこともある） | `## メモ` セクションの末尾                  |
| チャットの往復を転載 | チャットの「メモに写す」モード                    | `## AI とのやりとり` セクション（文書末尾） |

**メモから LLM へ送るものは無い。** 方向はチャット → メモの一方向だけで、推敲も要約も生成も
しない。前身が Phase 4 に置いていたもの（推敲・メモについての質問・ハイライトからの下書き生成）
はすべて落とす。理由は 3 つ。

- メモは「AI が書き換える対象」ではなく、ただの Markdown 文書のままでいられる。「ソースが正」
  という前提と食い合わない
- 前身が Phase 4 の最大の価値としていた「白紙のエディタ問題」は、挿入と転載の 2 経路が解く。
  読書という行為そのものがメモを育てるので、AI に下書きを作らせる必要が無い
- 前身が「本全体についての会話」のために並べていたスキーマ変更の 3 択（`chat_messages.selection_id`
  が NOT NULL かつ `selections` への FK）が、そもそも発生しない

## 既にあるもの

新しく発明が要る箇所を見誤らないために、流用できるものを先に並べる。

| 要るもの                             | 現状                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Markdown レンダリング                | `react-markdown` + `remark-gfm` + `rehype-highlight` + `mermaid` が依存にあり `ChatMessageBubble` で稼働中 |
| 内部リンクの横取り                   | `ChatMessageBubble` の `CitationLink` が `a` レンダラを差し替えて本の中を移動させている                    |
| 引用文からページを解決する経路       | `chatService.findPageNumber` / `GET /pdf/:pdfId/locate` / `#:~:text=` の一式が完成済み                     |
| ハイライトの保存                     | `useAskAboutSelection` の保存経路（`saveSelection` を DI 済み）                                            |
| デバウンス保存と離脱時 flush         | `useReadingStateSync` が手本。`save` と `debounceMs` を DI 済みで偽タイマーでテストできる                  |
| 狭い画面の全高シート                 | `chatSheetAtom` の `full` が `h-full`                                                                      |
| 入力中にショートカットが暴発しない   | `useKeyboardShortcuts` の `isEditableTarget` が `TEXTAREA` を既に除外している。追加対応は不要              |
| 失敗の運び方・zod スキーマ・SWR の型 | `resultFetcher` / `src/shared/schemas/` / `ApiError` のレールが敷かれている                                |

**新規に設計が要るのは保存の信頼性だけ**という見立ては変わらない。ただしそこは以下のとおり
広い。

## データと API

```
notes: id / pdf_id (unique, FK cascade) / body / version / created_at / updated_at
```

**`pdfs` に列を足さない。** `readPdf` / `storePdf` は drizzle が全列を明示列挙するため、列を
足すと本を開くたびに本文（実書籍で 213KB）に加えてメモまで D1 から読むことになる（CLAUDE.md の
「応答に使わない列を select しない」に反する）。別テーブルなら `GET /api/pdf/:pdfId` を一切
触らずに済み、本を開く経路への退行リスクがゼロになる。

エンドポイントは 2 本。`requireSession` が全ルートより先に登録されているので、どちらも黙って
守られる。

**`GET /api/pdf/:pdfId/note`** — `{ body, version }`。本は在るが note 行がまだ無ければ
`{ body: "", version: 0 }`。**PDF 自体が無ければ `PDF_NOT_FOUND` の 404**（「メモが空」と
「本が無い」は別の答えである）。

**`PUT /api/pdf/:pdfId/note`** — 本文は `{ body, version }`。`version` は読者が読み込んだ
ときの値。

```ts
// 200
{ version: number }

// 409
{
  error: { code: "NOTE_CONFLICT", message: string },
  current: { body: string, version: number },
}
```

**409 は封筒の中に競合相手の本文を積んで返す。** ここが `resultFetcher` の既定と噛み合わない
唯一の場所で、あれは非 2xx をすべて `ApiError` にし、拒否本文から `{ error: { code, message } }`
しか読まない。**素通しすると競合相手の本文が捨てられ、リベースも 3-way マージもできない。**
`NOTE_CONFLICT` を `ERROR_CODES` に足し、front は汎用の `resultFetcher` を変えずに、409 だけを
ドメインの結果へ翻訳する専用の `saveNote` を持つ。

```ts
type SaveNoteError = { type: "CONFLICT"; current: NoteSnapshot } | { type: "API"; cause: ApiError };
```

**サーバ側でも競合は障害ではなく通常の保存結果である。** 既存の `ServiceError`
（`NOT_FOUND` / `STORAGE`）を増やさず、note service が `SAVED` / `CONFLICT` の判別可能な
成功値を route へ返す。D1 を叩くのは route ではなく service（既存規約どおり `ResultAsync`）。

front と server が読む 200 / 409 のスキーマは `src/shared/schemas/note.ts` に 1 箇所だけ置く。

### 保存は 1 文の条件付き UPSERT

「先に UPDATE し、行が無ければ INSERT」にしてはいけない。**2 端末が同時に空のメモを読み、
どちらも `version: 0` で初めて保存すると、一方が `pdf_id` の unique 違反で 500 になる。**
初回作成と更新を 1 文にまとめる。

```sql
INSERT INTO notes (..., body, version) VALUES (..., :body, 1)
ON CONFLICT(pdf_id) DO UPDATE SET
  body = excluded.body,
  version = notes.version + 1,
  updated_at = excluded.updated_at
WHERE notes.version = :expected_version
RETURNING body, version;
```

`expected_version = 0` で行が無ければ version 1 を作り、行が在れば現在の version が一致した
ときだけ更新する。**`RETURNING` が 0 行なら競合**で、現在の `{ body, version }` を読み直して
`CONFLICT` として返す。読み直しより先にまた別の保存が進んでいたら、その時点で最も新しい状態を
返せばよい（読者に見せるのは「サーバはいまこうなっている」であって、特定の版ではない）。

## 保存の規約

**読書位置とは別の規約にする。** CLAUDE.md は読書位置について「保存に失敗しても再送はしない」
「後に書いた方が勝つ」と定めているが、**この規約をメモに持ち込むと文章が消える**。ページ番号を
失うことと段落を失うことは別の事故である。差分は 4 点。

**保存状態を常時見せる。** 読書位置は失敗したときだけ帯を出すが、メモは「保存済み / 未保存 /
保存中 / 保存失敗 / 競合」を常に出す。書いたものがサーバにあると確認できないエディタは
信用されない。

**`localStorage` にドラフトを鏡写しする。** 離脱時 flush は読書位置（数十バイト）なら安全だが、
育ったメモは `keepalive` の 64KB 上限を超えうる（下記「ドラフト」）。

**競合を検出する。** 端末をまたいで同じ本を開くのはこのアプリの前提そのもの（読書位置同期の
存在理由がそれ）。`version` 列 1 本と `WHERE` 句 1 つで済むうちに入れる。

**保存のたびに確認する。** 別の往復でサーバの状態を見に行くことはしない。`PUT` 自体が確認を
兼ねる。

### 書き込みは 1 つの note session に集約する

4 つの入口がそれぞれ勝手に `GET` / `PUT` すると、**別の端末より先に同じブラウザ自身が競合する**。
1 冊につき 1 つの session が、サーバ版・編集中の本文・保存キューをまとめて持つ。

```ts
type NoteSession = {
  baseBody: string;
  baseVersion: number;
  body: string;
  status: "saved" | "dirty" | "saving" | "failed" | "conflicted";
  saveError: string | null;
};
```

**保存は single-flight。** `PUT` の送信中に本文が変わっても 2 本目を並行して送らず、先の応答で
`baseBody` / `baseVersion` を進めてから、残っている変更を改めて送る。

- 応答時の `body` が送ったスナップショットと同じなら `saved`
- 応答時にさらに編集されていれば、新しい本文を保ったまま `dirty` として次を保存
- 409 で自動融合できれば、サーバ版を新しい base として融合後の本文を再送
- マーカーが残れば `conflicted` にし、**自動保存を止める**
- 競合を直したあとの明示的な保存は、409 が返したサーバ版の version を使う

**再送には上限を設ける。** 409 → 自動融合 → 再送は、別端末が保存を続けている間ループしうる。
上限に達したら `conflicted` に落として読者に委ねる。

置き場所は `BookReader`（`src/front/pages/AppPage.tsx` の中。両ペインの共通祖先）。メモタブ・
`PdfViewer`・チャットの転載モードへ状態と操作を渡す。**SWR の値を atom へ常時コピーしない**
——読み込み結果は `baseBody` / `baseVersion` の初期値として 1 度だけ入力し、そのあとは読者が
編集するクライアント状態を session が持つ（CLAUDE.md の「SWR が持っているものを atom へ写す
のは理由にならない」と、`useReadingLocation` が認めている「一度きりの入力」の線引きに従う）。

## 競合の解き方

409 を受けたときの振る舞いは、**その書き込みが位置に依存しない追記かどうかで分ける**。

### 位置に依存しない追記はリベースしてやり直す

**狭い画面のクイックメモ・選択付きクイックメモ・チャットの転載**は「決まったセクションの末尾に
足す」だけで、足す位置が本文の中身に依存しない。409 が返ったらサーバの最新本文を取り直し、
同じ追記をもう一度当てる。やり直しても意味が変わらないので、読者は競合が起きたことを知らなくて
よい。

**狭い画面の書き込み経路はこれしかない**（下記「画面」）ので、電話に競合の UI は要らない。
再試行には上限を設け、超えたときと通信に失敗したときは**入力を消さず**、理由をメモタブ内に出す。

### 広い画面の書き込みはすべてローカル本文へ当てる

**キャレット位置は本文に対する文字オフセットなので、別端末がその前を編集すると同じオフセットの
意味が変わる。** したがって広い画面では、次の 3 つをすべて現在のローカル本文へ適用し、通常の
自動保存と 3-way マージへ流す。**サーバへ別の `PUT` を投げる経路を作らない。**

- textarea の自由編集
- PDF の選択箇所をキャレットへ挿入
- チャットの往復を末尾へ転載

フォーカスが無いときも、ローカル本文の末尾へ挿入する。**未保存の自由編集を飛び越えて
サーバ版だけを書き換えない。**

### 自由編集の競合は 3-way マージ

読み込み時の本文（base）を session が持っているので、base / 自分 / サーバの 3-way マージが
成立する。

- **重なっていない編集は自動で融合する。** 別の段落を触っただけなら競合にならない
- **同じ行を両方が書き換えたときだけ**、`<<<<<<< 自分` / `=======` / `>>>>>>> サーバ` の
  マーカーを本文に差し込む。**メモは元々 Markdown のソースを textarea で編集しているので、
  それ自体が編集可能なマージ画面になる。** 専用の差分 UI は作らない
- マーカーが残っている間は自動保存を止め、読者が直して明示的に保存するまで待つ

**実装は `node-diff3` を使う。** jsdiff（`diff` パッケージ）の `merge` は、誤った結果を返す
不具合を理由に v8 で削除されている（そもそもあれは patch のマージで、ここで欲しい 3-way とは
別物だった）。`node-diff3` の `mergeDiff3(a, o, b, { labels })` は行配列を受け取り、ラベル付きの
マーカーを返す。

**文字列をそのまま渡さない。** 既定では空白単位に分割されるので、**行配列へ分割して行単位で
マージする**。末尾改行の有無を失わない変換を純粋関数として切り、単体テストする。

- 別の段落を編集した場合は自動で融合する
- 同じ行を編集した場合だけ競合マーカーが入る
- 空本文・末尾改行なし・連続する空行を往復しても本文が変わらない
- マーカーのラベルが `自分` / `サーバ` になる

参考: [jsdiff v8 release notes](https://github.com/kpdecker/jsdiff/blob/master/release-notes.md#800) /
[node-diff3](https://github.com/bhousel/node-diff3#3-way-diff-and-merging)

## ドラフト（`localStorage`）

**新旧を時刻で判定しない。** 端末間で時計は一致しないので、ドラフトは base を一緒に持つ。

```ts
// chatbook:note-draft:<pdfId>
type NoteDraft = {
  body: string;
  baseBody: string;
  baseVersion: number;
};
```

復帰の規則:

- `draft.body` とサーバ本文が同じならドラフトを削除する
- draft の base とサーバ版が同じなら、未保存ドラフトとして復帰を提案する
- サーバ版が進んでいれば、復帰を選んだときに draft / base / server を 3-way マージする
- **保存が成功し、現在の本文までサーバに載ったと確認できたときだけ削除する**

**ドラフトを作るのは広い画面だけ**（編集するのが広い画面だけなので）。狭い画面の投げ込みは
即座にサーバへ行き、手元に未送信の本文を残さない。ただし**広い画面で作った未保存ドラフトは、
ウィンドウのリサイズや端末の回転で狭いレイアウトになっても捨てない**——「狭い画面はドラフトを
新しく作らない」ことと「既にあるドラフトを消す」ことは別である。

JSON の破損と `QuotaExceededError` で画面を落とさない。後者は**ドラフトを守れなかったことを
保存状態の近くに出す**（黙って握りつぶすと、読者は保険があると思ったまま書き続ける）。

## 画面

### 広い画面

右ペインをタブにして、チャットとメモを切り替える（`ChatArea` の中。ペインの開閉と幅のハンドルは
今のまま）。3 ペインにも引き出しにもしないのは、どちらも PDF の表示領域を削るため。

メモタブは textarea + ライブプレビュー + ツールバー + 保存状態の表示。CodeMirror や ProseMirror は
入れない（重いうえ、ソースが正であることを保つのが結局いちばん強い）。

ツールバー（太字・見出し・リスト）は DOM に依存しない純粋関数に落ちる。

```ts
applyMarkdownCommand(text, selStart, selEnd, command): { text, selStart, selEnd }
```

プレビュー内の `p.42` リンクはページ遷移させず本の中を移動させたいので、`a` レンダラを
差し替えて内部リンクを横取りする（`CitationLink` と同じ形）。

### 狭い画面

シートに同じタブを置く。**メモタブはプレビューと 1 行入力欄だけで、編集はしない。** 電話で
起きるのは「気になった箇所を投げ込む」であって「腰を据えて文章を書く」ではなく、狭い textarea で
消耗する道を塞ぐ。

**この判断が「電話に競合の UI が要らない」を成立させている。** あとから電話に textarea を
足すなら、競合の扱いを設計し直すこと。

投げ込む口は 2 つ。`SelectionActionBar` の「メモに追加」（選択箇所 + メモ）と、選択せずに開く
1 行入力欄（メモのみ）。

## 積み方の規則

**過去の同名見出しを文書全体から探さない。** 探すと、読者がその見出しを書き換えたり移動したり
した瞬間に破綻する。ただし末尾のセクションを認識するには Markdown の構造を読む必要がある。

- 文書の末尾側から、**コードフェンスの外にある**レベル 2 見出しだけを調べる
- 最後の H2 が `## AI とのやりとり` なら、チャットの転載をその末尾へ足す
- 最後の H2 が AI セクションなら、**その直前の H2 が `## メモ` の場合だけ**クイックメモをそこへ
  足す
- 対象が末尾の所定位置に無ければ、過去の同名見出しは探さず、**新しいセクションを末尾に作る**
- 選択箇所の挿入はキャレット位置。フォーカスが無ければ末尾

すべて純粋関数。コードフェンス内の `## メモ`、末尾改行なし、CRLF、見出し前後の空行を単体
テストする。

積まれた文書はこうなる。

```markdown
（広い画面で書いた本文）

## メモ

- 3 章の説明は Raft の前提を省いている
- > 一貫性は 1 スレッドで担保される

  ここ、後で MVCC と比べる
  <sup>[p.42](?page=42&selection=01KZ...)</sup>

## AI とのやりとり

### これは結局どういう一貫性?

Durable Object は 1 スレッドで状態を持つので…

<sup>[p.42](?page=42&selection=01KZ...&chat=01KY...)</sup>
```

## 選択箇所の挿入はハイライトを作る

挿入操作は `selections` の行を 1 つ作る。`useAskAboutSelection` の保存経路をほぼそのまま
再利用でき、メモからその箇所へ戻る導線が既存の `?selection=` 復元だけで成立する。作らない場合、
メモ専用のアンカー機構をもう一系統持つことになる。

**本にマーカーが増えることは受け入れる。** メモに写すほど気になった箇所は、そもそも
ハイライトされていて欲しい箇所である。メモから引用を消してもハイライトは残るが、それは
ハイライトとして残っているだけなので直さない。

**アンカーはページ番号と引用文。** PDF に行番号という概念は無く、テキストレイヤーの span を
y 座標で束ねた擬似的な行はフォントや段組みで崩れるうえ、「p.42 の 17 行目」は読者にとって
意味を持たない。ページ番号と引用文は `/locate` と `#:~:text=` が既に使っている単位である。

**挿入したらメモを見せる。** 右ペインがチャットタブならメモタブへ切り替え、狭い画面なら
シートを上げる。`useAskAboutSelection` の「質問することはチャットを開くことでもある」と同じ
意味論で、書き込んだ先が畳まれたままにならないようにする。

**狭い画面のクイックメモも、選択箇所を伴うならハイライトを作る**（選択を伴わないものは作らない。
アンカーが無いため）。

### 2 つの書き込みの部分成功

挿入はハイライトの作成とメモの保存という **2 つの書き込み**を行う。順番と後始末を決めておく。

1. 先に selection を保存する
2. 成功して返った selection id で引用リンクを組み立てる
3. メモ本文へ挿入する
4. **メモの保存に失敗しても、作成済みの selection id と入力を保持する**
5. 再試行では selection を作り直さず、同じ id の引用を保存する

これで、メモの保存だけが失敗したときに**同じハイライトが増殖しない**。selection の保存自体が
失敗した場合は、既存の `useAskAboutSelection` と同じくポップオーバーと入力を残す。

## チャットの転載

**モードとして入る。** チャットの「メモに写す」を押すと、質問と回答のセットがひとまとまりで枠に
囲まれ、チェックボックスが付く。任意のセットを選んで確定すると、末尾の AI セクションへ積まれる。
全選択のチェックボックスも置く（外すと全部外れる）。

**1 往復を識別する id は、保存済み assistant message の id。** 次の 3 つは転載の対象にしない。

- ストリーム中の回答（まだ保存されていない）
- 保存に失敗して一時 id しかない回答（`CHAT_SAVE_FAILED` で画面には残るもの）
- 直前に assistant が無い孤立した user message

**重複防止は本文の走査で行う。** 引用リンクに写した往復の id を載せ
（`?page=42&selection=…&chat=<id>`）、モードに入ったときメモ本文を走査して、既に `chat=<id>` が
あるセットを「写し済み」として無効化する。全選択は写し済みを除いた残りを対象にする。
**409 のあと最新本文へ転載を再適用するときも `chat=<id>` を再確認し**、別端末が同じ往復を先に
写していたら追加を no-op にする。

**転記済みテーブルは作らない。** 本文が唯一の正であることの帰結として、**読者がメモから消せば
また写せるようになる**。消したということは要らなかったか書き直したかなので、これが正しい
振る舞いである。

量が多くなることは許容する（読者があとでメモを編集して削る）。

## ダウンロード

**アプリ内リンクはプレーンテキストへ落とす。** `?page=42&selection=...` は書き出した `.md` から
意味のあるリンクにならず、公開 URL へ絶対化してもログインの内側なので他人に渡せない。
`(p.42)` へ変換し、**Web 出典の通常リンクはそのまま残す**。

**書き出すのはサーバ版ではなく、画面にある現在の本文。** これで未保存の編集も手元へ退避できる。

ファイル名は PDF の最終拡張子を `.md` へ置き換え、OS で使えない文字を安全な文字へ変換する。
本文の変換もファイル名の生成も純粋関数にして単体テストする。

## フェーズ

上から順に、それぞれ単独で価値が出るように切る。

1. **メモ本体** — `notes` テーブル、2 本の API、note session、エディタ、保存（デバウンス・
   状態表示・ドラフト・`version` と 3-way マージ）
2. **PDF からの挿入** — ハイライトを作り、引用ブロックと `p.42` リンクを入れる。狭い画面の
   クイックメモもここ
3. **チャットの転載** — 「メモに写す」モード、チェックボックス、重複防止
4. **ダウンロード** — Markdown で書き出す

## テスト方針

- **純粋関数を先に切る。** `applyMarkdownCommand`、3 つの積み方、重複判定、行配列への分割と
  復元、マージ結果の解釈（自動融合できたか / マーカーが残ったか）はすべて DOM に依存しない
  関数にして jsdom で単体テストする
- **自動保存は `useReadingStateSync` と同じ形。** `save` と `debounceMs` を DI し、偽タイマーで
  進める
- **新しいエンドポイントは D1 に触るので `test/worker/**`\*\* に置く
- **E2E は fixture 共有の罠を踏む。** 3 つの spec は同じファイルの本を使うので同じ `pdfId` を
  共有する。各 spec の `openTestBook` がハイライトと読書位置をリセットしているのと同じく、
  **メモもリセットが要る**。忘れると先行テストの残骸で後続が落ちる
- マイグレーションを足すので `pnpm run db:migrate:local`。バインディングは増えないので
  `vp exec wrangler types` は不要
- 依存（`node-diff3`）を 1 つ足すので `pnpm-lock.yaml` が変わる
- 完了時に **CLAUDE.md を更新する**。とくに「メモの保存規約が読書位置と違う理由」と「狭い画面に
  textarea を置かないことが競合の扱いを決めている」ことは、あのドキュメントの粒度なら必ず
  書き残す対象になる

少なくとも次を確認する。

| 何を                                                                 | どこで              |
| -------------------------------------------------------------------- | ------------------- |
| version 0 の初回保存が競合しても 500 / unique 違反にならず片方が 409 | worker              |
| 存在しない PDF の GET / PUT が 404                                   | worker              |
| 409 の `current` が型検証され、front の `CONFLICT` へ届く            | worker + jsdom      |
| `PUT` 中に再編集しても新しい本文が消えず、保存が直列になる           | jsdom（偽タイマー） |
| 広い画面の未保存本文へ挿入したあと競合しても、位置と本文を失わない   | jsdom               |
| 3-way マージ（自動融合・マーカー・空本文・末尾改行・ラベル）         | jsdom（純粋関数）   |
| ドラフトの復帰、サーバ進行後の復帰マージ、破損 JSON、容量超過        | jsdom               |
| selection 成功・note 失敗からの再試行でハイライトが重複しない        | jsdom               |
| 同じ chat id を 2 端末が転載しても、競合後の再適用で重複しない       | jsdom               |
| ストリーム中・保存失敗・孤立 user message が転載対象にならない       | jsdom               |
| コードフェンス内の同名見出しを末尾セクションと誤認しない             | jsdom（純粋関数）   |
| ダウンロード本文からアプリ内リンクだけが `(p.N)` へ変換される        | jsdom（純粋関数）   |

## スコープ外

- 複数メモ、メモの一覧・検索・タグ
- 本をまたいだメモの横断（ノートブック的な使い方）
- リッチテキスト編集、WYSIWYG
- 画像の添付
- メモの共有・公開
- AI がメモを書き換えること（推敲・要約・下書き生成）
- 本全体を対象とした会話（前身の 4-b。`chat_messages.selection_id` が NOT NULL かつ
  `selections` への FK である問題は、この機能とは独立した別課題として残る）
- 狭い画面での自由編集

## 付録: レビューで変わったこと

実装前レビュー（2026-08-23）で本文へ織り込んだ変更。**どれも「動くつもりで動かない」経路を
潰したもの**なので、実装中に元へ戻したくなったらここを読むこと。

| 変わったこと                                                   | 元の設計の何が問題だったか                                                            |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| マージは jsdiff ではなく `node-diff3`                          | jsdiff の `merge` は v8 で削除済み。そもそも patch のマージで 3-way ではなかった      |
| 409 は `{ error, current }` の形にし、専用の `saveNote` で読む | `resultFetcher` は拒否本文から `{ error }` しか読まず、競合相手の本文が捨てられていた |
| 初回保存も条件付き UPSERT 1 文                                 | 2 端末が同時に `version: 0` で保存すると unique 違反で 500 になっていた               |
| 4 つの入口を 1 つの note session に集約、single-flight         | 入口ごとに GET / PUT すると、別端末より先に同じブラウザ自身が競合していた             |
| 広い画面の挿入・転載はローカル本文へ当てる（リベース対象外）   | キャレット位置は文字オフセットなので、前を編集されると再適用で意味が変わっていた      |
| ドラフトは base を同伴し、時刻で新旧を判定しない               | 端末間で時計が揃わないので「サーバ版より新しければ」が判定できなかった                |
| 挿入は selection を先に保存し、失敗時も id を保持              | メモの保存だけ失敗して再試行すると、同じハイライトが増殖していた                      |
| 末尾セクションはコードフェンスの外の H2 で判定                 | 「位置だけで決める」と言いながら、Markdown の構造を読む必要が残っていた               |
| 再送・再試行に上限を設ける                                     | 409 → 融合 → 再送が、別端末が保存を続ける間ループしえた                               |
| ダウンロードは内部リンクを `(p.N)` へ落とす                    | 書き出した `.md` からは開けないリンクがそのまま残っていた                             |

**実装担当の推奨はこの文書には置かない。** 誰が実装するかは実装のたびに変わる判断で、この文書は
残り続けるため。
