# 読書メモ機能 設計

- 種別: 確定設計（実装前）
- 対象: AI チャットとは別に、本ごとの Markdown 読書メモを取れるようにする機能
- 最終更新: 2026-08-23
- 前身: [`2026-08-19-reading-notes-design.md`](./2026-08-19-reading-notes-design.md)（検討段階。「決定待ち」を含む）

本を読みながら自分の言葉でメモを取り、PDF の選択箇所とチャットの往復をそこへ集める。
前身の文書が残していた 5 つの決定待ちはすべて埋め、**AI がメモを書き換える経路（前身の
Phase 4）は落とした**。この文書が正で、前身は検討の記録として残す。

## 何を作るのか

**本ごとに 1 枚の Markdown 文書。** メモが埋まる経路は 4 つで、書き手はどれも読者である。

| 経路                 | 入口                                              | 着地                                     |
| -------------------- | ------------------------------------------------- | ---------------------------------------- |
| 自分で書く           | 右ペインのメモタブ（広い画面のみ）                | キャレット位置                           |
| PDF の選択箇所を挿入 | `SelectionPopover` / `SelectionActionBar`         | キャレット位置。フォーカスが無ければ末尾 |
| クイックメモ         | 狭い画面の 1 行入力欄（選択箇所を伴うこともある） | `## メモ` セクションの末尾               |
| チャットの往復を転載 | チャットの「メモに写す」モード                    | `## AI とのやりとり` セクション（末尾）  |

**メモから LLM へ送るものは無い。** 方向はチャット → メモの一方向だけで、推敲も要約も
生成もしない。前身が Phase 4 に置いていたもの（推敲・メモについての質問・ハイライトからの
下書き生成）はすべて落とす。理由は 3 つ。

- メモは「AI が書き換える対象」ではなく、ただの Markdown 文書のままでいられる。Phase 1 の
  「ソースが正」という前提と食い合わない
- 前身が Phase 4 の最大の価値としていた「白紙のエディタ問題」は、挿入と転載の 2 経路が
  解く。読書という行為そのものがメモを育てるので、AI に下書きを作らせる必要が無い
- 前身が「本全体についての会話」のためにスキーマ変更の 3 択を並べていた問題（`chat_messages.selection_id`
  が NOT NULL かつ `selections` への FK）が、そもそも発生しない

## 既にあるもの

新しく発明が要る箇所を見誤らないために、流用できるものを先に並べる。

| 要るもの                             | 現状                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Markdown レンダリング                | `react-markdown` + `remark-gfm` + `rehype-highlight` + `mermaid` が依存にあり `ChatMessageBubble` で稼働中 |
| 内部リンクの横取り                   | `ChatMessageBubble` の `CitationLink` が `a` レンダラを差し替えて本の中を移動させている                    |
| 引用文からページを解決する経路       | `chatService.findPageNumber` / `GET /pdf/:pdfId/locate` / `#:~:text=` の一式が完成済み                     |
| ハイライトの保存                     | `useAskAboutSelection` の保存経路（`saveSelection` を DI 済み）                                            |
| デバウンス保存と離脱時 flush         | `useReadingStateSync` がそのまま手本。`save` と `debounceMs` を DI 済みで偽タイマーでテストできる          |
| 狭い画面の全高シート                 | `chatSheetAtom` の `full` が `h-full`。上流から取り込み済み                                                |
| 入力中にショートカットが暴発しない   | `useKeyboardShortcuts` の `isEditableTarget` が `TEXTAREA` を既に除外している。追加対応は不要              |
| 失敗の運び方・zod スキーマ・SWR の型 | `resultFetcher` / `src/shared/schemas/` / `ApiError` のレールが敷かれている                                |

**新規に設計が要るのは保存の信頼性だけ**という前身の見立ては変わらない。

## データと API

```
notes: id / pdf_id (unique, FK cascade) / body / version / created_at / updated_at
```

**`pdfs` に列を足さない。** `readPdf` / `storePdf` は drizzle が全列を明示列挙するため、
列を足すと本を開くたびに本文（実書籍で 213KB）に加えてメモまで D1 から読むことになる
（CLAUDE.md の「応答に使わない列を select しない」に反する）。別テーブルなら
`GET /api/pdf/:pdfId` を一切触らずに済み、本を開く経路への退行リスクがゼロになる。

エンドポイントは 2 本。`requireSession` が全ルートより先に登録されているので、どちらも
黙って守られる。

| メソッド | パス                   | 返すもの                                                      |
| -------- | ---------------------- | ------------------------------------------------------------- |
| `GET`    | `/api/pdf/:pdfId/note` | `{ body, version }`。まだ無ければ `{ body: "", version: 0 }`  |
| `PUT`    | `/api/pdf/:pdfId/note` | 200 `{ version }` / 409 `{ body, version }`（サーバ側の現状） |

`PUT` の本文は `{ body, version }`。`version` は読者が読み込んだときの値で、サーバは
`WHERE version = ?` を条件に書き、**0 行更新なら 409** を返す。front と server が交わす形は
`src/shared/schemas/note.ts` に zod スキーマとして 1 箇所だけ置く。

**行が無ければ `PUT` が作る。** メモを持たない本は `notes` に行が無く、`GET` は
`{ body: "", version: 0 }` を返す。読者が最初に保存したとき `version: 0` を条件に行を作り、
以後**保存が成功するたび `version` が 1 つ増える**。

## 保存の規約

**読書位置とは別の規約にする。** CLAUDE.md は読書位置について「保存に失敗しても再送は
しない」「後に書いた方が勝つ」と定めているが、**この規約をメモに持ち込むと文章が消える**。
ページ番号を失うことと段落を失うことは別の事故である。差分は 4 点。

**保存状態を常時見せる。** 読書位置は失敗したときだけ帯を出すが、メモは「保存済み /
未保存 / 保存失敗」を常に出す。書いたものがサーバにあると確認できないエディタは信用されない。

**`localStorage` にドラフトを鏡写しする。** 離脱時 flush は読書位置（数十バイト）なら
安全だが、育ったメモは `keepalive` の 64KB 上限を超えうる。次に開いたときサーバ版より
新しければ復帰を提案する。**編集するのは広い画面だけなので、ドラフトを持つのも広い画面だけ**——
狭い画面の投げ込みは即座にサーバへ行き、手元に未送信の本文を残さない。

**競合を検出する。** 端末をまたいで同じ本を開くのはこのアプリの前提そのもの（読書位置
同期の存在理由がそれ）。`version` 列 1 本と `WHERE` 句 1 つで済むうちに入れる。

**保存のたびに確認する。** 別の往復でサーバの状態を見に行くことはしない。`PUT` 自体が
確認を兼ねる。

## 競合の解き方

409 を受けたときの振る舞いは、**書き込みが追記かどうかで分ける**。

### 追記はリベースしてやり直す

クイックメモ・チャットの転載・選択箇所の挿入は「決まった位置に足す」だけで、足す内容が
本文の中身に依存しない。したがって 409 が返ったら**サーバの最新本文を取り直して同じ追記を
もう一度当てる**。やり直しても意味が変わらないので、読者は競合が起きたことを知らなくてよい。

**狭い画面の書き込み経路はこれしかない**（下記「画面」）ので、電話に競合の UI は要らない。

### 自由編集は 3-way マージ

広い画面の textarea だけが本当に競合しうる。読み込み時の本文（base）をクライアントが
持っているので、base / 自分 / サーバの 3-way マージが成立する。

- **重なっていない編集は自動で融合する。** 別の段落を触っただけなら競合にならない
- **同じ箇所を両方が書き換えたときだけ**、`<<<<<<< 自分` / `=======` / `>>>>>>> サーバ` の
  マーカーを本文に差し込む。**メモは元々 Markdown のソースを textarea で編集しているので、
  それ自体が編集可能なマージ画面になる**。専用の差分 UI は作らない
- マーカーが残っている間は**自動保存を止める**。読者が直して明示的に保存するまで待つ
- マージの実装は jsdiff（`diff` パッケージ）の 3-way マージを使う。自前で書くと LCS 差分から
  書くことになり、競合の頻度（利用者 1 人）に対して割に合わない

## 画面

### 広い画面

右ペインをタブにして、チャットとメモを切り替える（`ChatArea` の中。ペインの開閉と幅の
ハンドルは今のまま）。3 ペインにも引き出しにもしないのは、どちらも PDF の表示領域を削るため。

メモタブの中身は textarea + ライブプレビュー + ツールバー + 保存状態の表示。CodeMirror や
ProseMirror は入れない（重いうえ、ソースが正であることを保つのが結局いちばん強い）。

ツールバー（太字・見出し・リスト）は DOM に依存しない純粋関数に落ちる。

```ts
applyMarkdownCommand(text, selStart, selEnd, command): { text, selStart, selEnd }
```

プレビュー内の `p.42` リンクはページ遷移させず本の中を移動させたいので、`a` レンダラを
差し替えて内部リンクを横取りする（`CitationLink` と同じ形）。

### 狭い画面

シートに同じタブを置く。**メモタブはプレビューと 1 行入力欄だけで、編集はしない。**
電話で起きるのは「気になった箇所を投げ込む」であって「腰を据えて文章を書く」ではなく、
狭い textarea で消耗する道を塞ぐ。**この判断が「電話に競合の UI が要らない」を成立させている**
ので、あとから電話に textarea を足すなら競合の扱いを設計し直すこと。

投げ込む口は 2 つ。`SelectionActionBar` の「メモに追加」（選択箇所 + メモ）と、選択せずに
開く 1 行入力欄（メモのみ）。

## 積み方の規則

**どれも文書全体を検索せず、位置だけで決める。** 「`## AI とのやりとり` という見出しを
文書中から探す」とやると、読者がその見出しを書き換えたり移動したりした瞬間に破綻する。
位置で決めれば、読者が何をしても壊れない（見出しを消せば次から新しく作られ、途中へ
移動させればそこは以後放置されて末尾に新しくできる）。すべて純粋関数。

| 何を           | どこへ                                                                           |
| -------------- | -------------------------------------------------------------------------------- |
| チャット転載   | 文書の末尾。末尾が `## AI とのやりとり` ならその下に足し、違えば見出しごと作る   |
| クイックメモ   | `## メモ` セクションの末尾。AI セクションがあればその 1 つ上、無ければ文書の末尾 |
| 選択箇所の挿入 | キャレット位置。フォーカスが無ければ末尾                                         |

積まれた文書はこうなる。

```markdown
（広い画面で書いた本文）

## メモ

- 3 章の説明は Raft の前提を省いている
- > 一貫性は 1 スレッドで担保される

  ここ、後で MVCC と比べる
  <sup>[p.42](?page=42&selection=01KZ...)</sup>

## AI とのやりとり

### これは結局どういう一貫性?

Durable Object は 1 スレッドで状態を持つので…

<sup>[p.42](?page=42&selection=01KZ...&chat=01KY...)</sup>
```

## 選択箇所の挿入はハイライトを作る

挿入操作は `selections` の行を 1 つ作る。`useAskAboutSelection` の保存経路をほぼそのまま
再利用でき、メモからその箇所へ戻る導線が既存の `?selection=` 復元だけで成立する。
作らない場合、メモ専用のアンカー機構をもう一系統持つことになる。

**本にマーカーが増えることは受け入れる。** メモに写すほど気になった箇所は、そもそも
ハイライトされていて欲しい箇所である。メモから引用を消してもハイライトは残るが、それは
ハイライトとして残っているだけなので直さない。

**挿入したらメモを見せる。** 右ペインがチャットタブならメモタブへ切り替え、狭い画面なら
シートを上げる。`useAskAboutSelection` の「質問することはチャットを開くことでもある」と
同じ意味論で、書き込んだ先が畳まれたままにならないようにする。

**狭い画面のクイックメモも、選択箇所を伴うならハイライトを作る**（選択を伴わないものは
作らない。アンカーが無いため）。

**アンカーはページ番号と引用文。** PDF に行番号という概念は無く、テキストレイヤーの span を
y 座標で束ねた擬似的な行はフォントや段組みで崩れるうえ、「p.42 の 17 行目」は読者にとって
意味を持たない。ページ番号と引用文は `/locate` と `#:~:text=` が既に使っている単位である。

## チャットの転載

**モードとして入る。** チャットの「メモに写す」を押すと、質問と回答のセットがひとまとまりで
枠に囲まれ、チェックボックスが付く。任意のセットを選んで確定すると、末尾の AI セクションへ
積まれる。全選択のチェックボックスも置く（外すと全部外れる）。

**重複防止は本文の走査で行う。** 引用リンクに写した往復の id を載せ（`?page=42&selection=…&chat=<id>`）、
モードに入ったときメモ本文を走査して、既に `chat=<id>` があるセットを「写し済み」として
無効化する。全選択は写し済みを除いた残りを対象にする。

**転記済みテーブルは作らない。** 本文が唯一の正であることの帰結として、**読者がメモから
消せばまた写せるようになる**。消したということは要らなかったか書き直したかなので、これが
正しい振る舞いである。

量が多くなることは許容する（読者があとでメモを編集して削る）。

## フェーズ

上から順に、それぞれ単独で価値が出るように切る。

1. **メモ本体** — `notes` テーブル、2 本の API、エディタ、保存（デバウンス・状態表示・
   `localStorage` ドラフト・`version` と 3-way マージ）
2. **PDF からの挿入** — ハイライトを作り、引用ブロックと `p.42` リンクを入れる。
   狭い画面のクイックメモもここ
3. **チャットの転載** — 「メモに写す」モード、チェックボックス、重複防止
4. **ダウンロード** — Markdown で書き出す

## テスト方針

- **純粋関数を先に切る。** `applyMarkdownCommand`、3 つの積み方、重複判定、マージ結果の
  解釈（自動融合できたか / マーカーが残ったか）はすべて DOM に依存しない関数にして jsdom で
  単体テストする
- **自動保存は `useReadingStateSync` と同じ形。** `save` と `debounceMs` を DI し、偽タイマーで
  進める。409 とリベース再試行、マーカーが残っている間は自動保存が止まることもここで見る
- **新しいエンドポイントは D1 に触るので `test/worker/**`** に置く。`version` が合わないときに
  409 になることと、**本文が書き換わっていないこと**を見る
- **E2E は fixture 共有の罠を踏む。** 3 つの spec は同じファイルの本を使うので同じ `pdfId` を
  共有する。各 spec の `openTestBook` がハイライトと読書位置をリセットしているのと同じく、
  **メモもリセットが要る**。忘れると先行テストの残骸で後続が落ちる
- マイグレーションを足すので `pnpm run db:migrate:local`。バインディングは増えないので
  `vp exec wrangler types` は不要
- 依存を 1 つ足すので `pnpm-lock.yaml` が変わる
- 完了時に **CLAUDE.md を更新する**。とくに「メモの保存規約が読書位置と違う理由」と
  「狭い画面に textarea を置かないことが競合の扱いを決めている」ことは、あのドキュメントの
  粒度なら必ず書き残す対象になる

## スコープ外

- 複数メモ、メモの一覧・検索・タグ
- 本をまたいだメモの横断（ノートブック的な使い方）
- リッチテキスト編集、WYSIWYG
- 画像の添付
- メモの共有・公開
- AI がメモを書き換えること（推敲・要約・下書き生成）
- 本全体を対象とした会話（前身の 4-b。`chat_messages.selection_id` が NOT NULL かつ
  `selections` への FK である問題は、この機能とは独立した別課題として残る）
- 狭い画面での自由編集
